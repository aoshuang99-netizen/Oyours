1 · 闭环全景（端到端）

① 注册→ ② 邮箱验证→ ③ OAuth1.0a 授权→ ④ token 持久化入库→ ⑤ 加载(人格+状态)→ ⑥ 移动端设备池分配指纹+UA→ ⑦ 五阶段调度循环→ ⑧ 真实动作(API+移动消费)→ ⑨ 持久化+指标→ ⑩ 看板监控→ ⑪ 反馈(推进/重授权/跳过/自愈)↺ 回到 ⑦

闭环关键点：每一步都有真实输出（真实 token / 真实 post_url / 真实移动会话），失败即停并如实记录；阶段推进由 dayOfLife 阈值自动驱动；停滞由看门狗自愈；Tumblr 限流由 429 回退吸收。

2 · 账号准入与凭证管理（末梢细节）

  • 16 真实账号：13 个持有真实 email + （可登录 Tumblr 移动网页，支撑移动消费会话），3 个仅 token-only（无密码，走 API 保底，不做 UI 会话）。
  • 重授权流程：request_token → authorize → → token 持久化；OAuth App 需用户先在 Tumblr 注册拿 consumer_key/secret 才能真实发布。
  • 凭证失效检测：API 返回 401/403 → 触发重授权事件，状态置为需重授权，看板标红，不伪造成功。
  • 终止账号：status==='terminated' 在 engine.load() 直接过滤，绝不纳入养号循环（历史上已剔除 y7jxcqge 等）。
  • 数据隔离：3003 服务只读 / / ，只写 tumblr_nurture / tumblr_persona / tumblr_device，与主服务(3002)零写竞争。

8 · 429 限流自愈回退 NEW

关键发现（2026-08-18）：Tumblr 对共享 app-key/IP（10808 代理）返回 429 "Limit Exceeded"，原引擎在限流下仍持续 hammering，加重封锁且让 lastApi 冻结。修复为 429 感知回退：
  • 命中 429（读端点 /user/dashboard、/tagged 或写端点）→ 进入全局 API 冷却 20 分钟（_apiCooldownUntil）。
  • 冷却期内暂停所有 API 互动动作（含读调用，避免重复触发），但移动端消费会话照常进行（浏览器行为，维系真人足迹）。
  • 读端点加 5 分钟短缓存（_cacheGet/_cacheSet），跨账号/跨 tick 复用，降低限流概率。
  • 看板实时显示冷却倒计时（橙色横幅）。

9 · 调度与时序（末梢细节）

  • Tick：90s 调度循环（_tickMs=90000），真实用户是零星使用而非批量刷。
  • nextActionAt：每动作后高斯抖动错峰（P2 ~25min±13、P4 ~15min±8）。
  • 移动会话先于 API 互动：tickAccount 先 _runDeviceSession 再执行阶段动作。
  • 错峰活跃窗口：_inActiveWindow 按 persona 时区，非活跃时段不动作（真人作息）。
  • 偶发跳过 + 动作顺序随机：模拟真人；动作间延迟高斯（like 1.5s / follow 4s / reblog 3s / 思考 8s）。
  • 日界：_todayKey()=UTC日期，每日上限自然重置。

10 · 持久化与恢复

  • DataStore 三集合全部登记 prune：tumblr_nurture{maxKeep:60}、tumblr_persona{maxKeep:60}、tumblr_device{maxKeep:60}。
  • 状态 reload 后 syncDeviceUA() 同步每账号移动 UA 到 publisher，使 API 足迹与移动网页指纹一致。
  • 重启不丢失进度（phase / day / totalActions / 设备型号），看板首会话前即显示设备型号。

11 · 自愈看门狗 + 代际守卫 NEW

  • 停滞看门狗：监听每次完整 nurture:tick 时间戳；若 >15 分钟无推进（如 chromium 15 上下文长时间运行卡死、事件循环被拖死 → 循环"静默死亡"但进程看似存活），自动 engine.stop() + devicePool.closeAll() + 重建浏览器池 + 重启，并 console.error 记录。
  • 代际守卫：start() 自增 _gen，loop() 捕获 myGen，被新一次 start/看门狗取代时立即退出，防止陈旧挂起循环重复动作。
  • 验证：重启后循环存活、设备池在线、429 回退生效、循环不崩溃。

16 · 已知风险与下一步

根因待解：429 源于共享 OAuth app-key + 单一代理出口 IP(10808→BandwagonHost VPS) 被 Tumblr 聚合限流。代码层面已用冷却+缓存缓解，但要从根本解除需：
  • 更多出口 IP：每账号/每小组独立代理（当前 proxy-pool.json 仅含单个 relay，需扩展）。
  • 多个 OAuth App：分散 consumer key 降低单 key 限流概率（需用户注册多个 Tumblr App）。
  • 降频：当前已保守（每号每 tick 1 动作），可进一步拉长 nextActionAt。
  • 阶段推进：P3（day≥7 ≈ 08-21）、P4（day≥14 ≈ 08-28）将自动触发。
  • 3 个 token-only 账号：仅 API 保底，无移动 UI 会话（凭证所限，如实标注）。
  • 进程守护：建议给 3003 加守护/开机自启，配合看门狗实现无人值守。
  • 长期质量指标：关注 followers/notes 真实增长、互动回粉率，作为养号质量反馈。

本计划覆盖从账号准入到成熟运营的全链路末梢细节；所有执行遵循零假数据、保守上限、反关联、隔离线上 50 云手机四大原则。代码已落地并端到端验证，服务运行于 http://localhost:3003 。
